Modern HTTP versions

Familiar request meanings remain useful even as the delivery mechanism changes.

HTTP/1.1's remaining ordering problem

HTTP/1.1 can pipeline requests, meaning a client sends another request before the earlier response finishes. The server must still send the corresponding responses in their request order.

If a large response comes first, a smaller later response can wait behind it. This application-level ordering constraint is often described as head-of-line blocking. Opening additional connections can provide parallelism, but adds connection overhead.

The limitation helps explain the next major version. A page with many resources benefits from being able to interleave their delivery rather than forcing every response through one ordered sequence.

            One pipelined HTTP/1.1 connection, simplified:
Requests:   A, then B
Responses:  A must precede B

A slow first response can delay a ready second response.

Read more: RFC 9112: HTTP/1.1.

SPDY and the move toward HTTP/2

As pages accumulated scripts, images, and other resources, connection overhead became harder to ignore. Google's experimental SPDY protocol explored ways to improve delivery and helped provide a basis for HTTP/2.

HTTP/2 was standardized in 2015. It retained the familiar meaning of methods, statuses, and fields while changing how messages were encoded and carried. Developers could continue writing normal resources rather than replacing the whole web application model.

That continuity is a major reason the history matters. A newer delivery mechanism could address performance problems while existing resource addresses and application behavior remained understandable.

Read more: MDN: Evolution of HTTP, RFC 9113: HTTP/2.

HTTP/2 frames and multiplexed streams

HTTP/2 divides communication into binary frames associated with streams. Several streams can share one connection, allowing parts of different responses to be interleaved. A slow application response no longer has to force every response into HTTP/1.1's ordering pattern.

Header compression with HPACK reduces repeated field information. This is separate from compressing a response body such as an HTML file. The protocol changes how both control information and content travel.

A stream identifier keeps the pieces associated with the correct exchange. The client can reconstruct several logical responses even though their frames share a connection.

            One HTTP/2 connection, simplified:
Stream 1: HTML frames
Stream 3: stylesheet frames
Stream 5: image frames

Frames from these streams may be interleaved.

Read more: RFC 9113: HTTP/2.

Why TCP still matters in HTTP/2

HTTP/2 multiplexing addresses response ordering at the HTTP layer, but its streams share a TCP connection. TCP delivers an ordered byte stream. Missing data can delay delivery of later received bytes until the gap is repaired.

As a result, packet loss can hold up data belonging to several HTTP/2 streams. This is a transport-level constraint, even when the individual HTTP responses are logically independent.

I would distinguish those layers before saying that HTTP/2 completely removes head-of-line blocking. It improves one ordering problem while still depending on the behavior of the transport beneath it.

Read more: RFC 9113: HTTP/2, RFC 9114: HTTP/3.

QUIC supplies a different transport

QUIC, standardized in RFC 9000 in 2021, is a transport protocol carried over UDP. It adds reliable delivery, congestion control, and multiple streams rather than assuming that an application can simply abandon missing data.

Ordered delivery occurs within a stream. Missing data on one stream does not inherently prevent another stream from making progress, although shared congestion and network conditions can still affect the connection overall.

QUIC also uses connection identifiers to support a connection across certain address changes. That can help when a device's network path changes. It does not mean every application will survive every network interruption.

Read more: RFC 9000: QUIC.

HTTP/3 maps HTTP onto QUIC

RFC 9114 defined HTTP/3 in June 2022. It maps HTTP exchanges onto QUIC streams and uses QPACK for field compression. Its design accommodates transport behavior that differs from HTTP/2's ordered TCP connection.

The request's purpose remains recognizable. A GET still requests a representation, and a 404 still communicates a missing target representation. The version changes the delivery mechanism while preserving shared HTTP semantics.

HTTP/3 can help avoid blocking unrelated streams behind missing transport data. It is not automatically faster for every site or network. Deployment conditions, connection setup, and the resources being transferred still affect the result.

Read more: RFC 9114: HTTP/3, RFC 9110: HTTP Semantics, RFC 9000: QUIC.

Current standards and future priorities

The 2022 specifications separate shared semantics, caching, and version-specific message delivery. RFC 9110 defines common meaning, while RFC 9111 covers caching and RFCs 9112–9114 describe the major versions. This organization makes the shared foundation easier to distinguish from transport details.

I expect continued work to focus on efficient delivery under imperfect network conditions and on compatibility with existing applications. That is an interpretation of the design problems addressed by HTTP/2, HTTP/3, and QUIC, rather than a promise about a future numbered version.

For my own development work, I would first verify correctness, then measure performance. Reducing unnecessary resources and using sensible caching can matter alongside the protocol negotiated by the host.
