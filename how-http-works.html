How HTTP works

A request names an action and a resource. The response describes what happened.

HTTP's role in a website

HTTP means Hypertext Transfer Protocol. It operates at the application layer, where a client requests a resource and a server responds. A browser is one kind of client, although programs that retrieve data can use HTTP as well.

HTML describes document structure, CSS controls presentation, and HTTP carries representations of resources between systems. An HTTP response might contain an HTML page, an image, or structured data rather than a complete website.

I find this separation useful when diagnosing a problem. Correct HTML cannot repair a missing server resource. A working response also does not guarantee that the page's content or layout is useful.

Read more: MDN: Overview of HTTP, RFC 9110: HTTP Semantics.

Reading a request and response

In HTTP/1.1, a request starts with a method, a target, and a protocol version. Header fields add information such as the intended host. A blank line separates those fields from any message body.

A response starts with its version and status. Content-Type describes the representation, so a client can distinguish HTML from another format. The example below omits fields and body details to make that structure easier to follow.

HTTP/2 and HTTP/3 carry the same basic information through binary framing. A readable HTTP/1.1 example explains the concepts, but it is not a literal picture of every version's wire format.

GET /lesson.html HTTP/1.1

Host: example.com



HTTP/1.1 200 OK

Content-Type: text/html; charset=utf-8



[HTML document body]

Read more: MDN: HTTP messages, RFC 9112: HTTP/1.1.

Methods describe the requested action

GET requests a representation of a resource. HEAD requests similar response information without response content. POST asks a resource to process supplied content, while PUT requests replacement of the target resource's state.

Safe methods have read-only intended semantics. Idempotent methods have the same intended effect when an identical request is repeated. PUT is idempotent, although repeating it can still produce different response messages.

These distinctions matter when a connection fails. Retrying a retrieval is different from repeating a purchase submission. I would choose methods according to the action's meaning rather than treating every request as interchangeable.

GET /articles/7       retrieve an article

HEAD /articles/7      retrieve response metadata

POST /orders         process a new order submission

PUT /profiles/7      replace that profile's state

Read more: MDN: Request methods.

Status codes make outcomes recognizable

The first digit groups a response into a broad category. Codes beginning with 1 provide information, 2 indicate success, 3 concern redirection, 4 indicate client errors, and 5 indicate server errors.

A 200 response commonly accompanies a successful retrieval. A 404 means the server did not find a current representation of the target, while a 500 reports an unexpected server condition. The number gives software a predictable signal beyond the page's visible wording.

I would read the exact code before changing a broken page. An incorrect file path and an unavailable application can look similar to a visitor, but they call for different repairs.

200 OK                  successful request

301 Moved Permanently   resource has a new permanent URI

404 Not Found           target representation not found

500 Internal Server Error   unexpected server condition

Read more: MDN: Status codes.

Caching avoids unnecessary transfers

A cache stores a response so that a later request may reuse it. Browser caches serve an individual user, while shared caches can serve multiple users. Correct reuse reduces traffic and avoids repeatedly downloading unchanged resources.

Cache-Control supplies instructions. max-age describes freshness lifetime. no-cache permits storage but requires successful validation before reuse, while no-store directs a cache not to store the response.

I would give a versioned stylesheet and a private account response different policies. A faster page is useful, but a cache must not reuse personal content as though it were a public image.

Cache-Control: public, max-age=3600

An eligible shared response can remain fresh for one hour.



Cache-Control: no-store

A cache must not store this response.

Read more: RFC 9111: HTTP Caching.

Validation checks whether a copy changed

A stored response can have a validator such as an ETag. When that copy needs validation, the client can send If-None-Match with the saved tag. The server compares it with the current representation.

If the condition indicates that the cached copy is still usable, a 304 Not Modified response allows reuse without sending the full representation again. Validation still involves an exchange, so it differs from reusing a response that remains fresh.

For a text-heavy site, this avoids repeatedly transferring identical content. It also shows why a status in the 3xx range does not always mean that the visitor must follow a new address.

Earlier response:  ETag: "lesson-v2"

Later request:     If-None-Match: "lesson-v2"

Unchanged result:  304 Not Modified



The stored representation supplies the content.

Read more: RFC 9111: HTTP Caching, RFC 9110: HTTP Semantics, MDN: Status codes.

Cookies connect otherwise separate requests

HTTP is stateless, so an exchange does not inherently establish an ongoing user session. A server can send Set-Cookie, and the browser can include an applicable Cookie field in later requests. Applications can use that identifier to connect requests with stored session data.

Cookie attributes control parts of that behavior. Secure restricts transmission to secure connections, while HttpOnly prevents access through JavaScript's document.cookie. SameSite helps limit when cookies accompany requests originating from another site.

A cookie should not be treated as harmless simply because it is small. An exposed session identifier can matter as much as other login information, and a site should store only the information it needs.

Illustrative session cookie:

Set-Cookie: session=example; Secure; HttpOnly; SameSite=Lax



A later applicable request may include:

Cookie: session=example

Read more: MDN: HTTP cookies.

HTTPS protects the exchange in transit

HTTPS uses HTTP with a secure transport. TLS provides encryption, integrity protection, and authentication of the server through its certificate. These protections make it harder for an intermediary to read or alter an exchange.

Encryption does not establish that a website's claims are honest. A malicious site can also use HTTPS. The protection concerns the connection and the authenticated endpoint, while application security still depends on how the site handles information.

For a real form, I would use HTTPS and validate submitted values on the server. Choosing POST alone does not encrypt the message, and changing the HTTP version does not repair an unsafe application.

Read more: MDN: Transport Layer Security, RFC 9110: HTTP Semantics.

APIs, origins, and CORS

An application can use HTTP to retrieve structured data from an API. A page on one origin may request data from another, but the browser's same-origin protections affect whether its script may read the response.

CORS uses response fields to describe permitted cross-origin access. Some requests require a preliminary OPTIONS exchange called a preflight. The server's policy and the browser's enforcement work together.

CORS is not a replacement for authentication. A developer should still protect private resources on the server. I would investigate a cross-origin browser error as a policy issue rather than assuming that the API is offline.

A server may explicitly allow a requesting origin:

Access-Control-Allow-Origin: https://example.com



This permits relevant browser access under CORS rules.

It does not identify or authenticate an individual user.

Read more: MDN: CORS.

Using the browser's Network panel

The Network panel in browser developer tools lists resource requests and their outcomes. Selecting an entry exposes details such as request and response fields, timing, and the returned content. Recording needs to be active while the page loads.

For a missing stylesheet, I would reload with the panel open, locate the CSS request, and inspect its status and requested address. A 404 suggests checking the deployed path before rewriting the stylesheet's rules.

A protocol column can help distinguish the negotiated HTTP version. Cache settings also affect observations, so I would note whether the test used the normal cache or deliberately disabled it. These are investigation steps, not measurements of this example site.

Read more: Chrome: Network panel overview.
